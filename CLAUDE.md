# Camelot: notes for Claude Code sessions

Camelot is a learning project: the Excalibur ISA (RV64IMA + Zicsr + Zifencei, M/S/U, Sv48 paging (Sv39 too), Xcal extensions; its RV32/Sv32 form kept until #159), the Grail emulator, the Merlin toolchain (merlin-as, merlin-ld, merlin-objdump, merlin C-subset compiler) and the Camelot OS. The spec is `docs/excalibur-spec.md`; the roadmap is its §11 and the tracking issue on GitHub (label `roadmap`).

## Picking up work

- Work comes from GitHub issues. Each one has a goal, spec references, acceptance criteria and dependencies. Check that its dependencies are merged before starting.
- Any open issue can be implemented. Code in the core pieces (encoder, linker relocations, compiler codegen) should stay readable and well commented, since it doubles as study material.
- If the spec is ambiguous or you change a design decision, update `docs/excalibur-spec.md` in the same PR.

## Hard rules

- **Rust, std only.** No crates in any `Cargo.toml`, including dev-dependencies. `Cargo.lock` must list only workspace crates. Windows APIs go through hand-written `extern "system"` FFI.
- **Windows-native.** Everything must build and run with `cargo` on Windows (and Linux). No WSL, no QEMU, no GCC cross toolchain. Build helpers are Rust (tests, `cargo xtask`-style binaries), not shell scripts. Existing `scripts/*.sh` are only for regenerating committed reference files with LLVM.
- **LLVM is a reference, not a dependency.** clang, ld.lld, llvm-mc and llvm-objdump (official Windows LLVM installer) may be used to produce golden files and to validate output, but `cargo test` must pass without them. Commit expected outputs.
- **No AI attribution anywhere**: no `Co-Authored-By` trailers, no "Generated with" lines, no session links, no Claude footers in commits, PRs, issues, comments or code.

## Layout

```
crates/excalibur        encodings, decoder, disassembler (shared by every tool), for RV32 and RV64: decode and Syntax take the width (Xlen); tests/disasm.rs checks both against llvm-objdump's text for tests/golden/rv{32,64}.s (scripts/gen-excalibur-golden.sh)
crates/elf              ELF reader, ELF32 and ELF64 alike (grail, merlin-objdump, merlin-ld), DWARF line tables (src/lines.rs: merlin-objdump -l, merlin-dbg) and compile units (src/units.rs: their address ranges and function names, which line table and name an address has for merlin-objdump -l, as LLVM's symbolizer finds them) and every debugging information entry as a tree (src/dies.rs: merlin-dbg's variables and types); tests/llvm.rs reads RV32 and RV64 files clang and ld.lld made as llvm-readelf and llvm-dwarfdump print them (scripts/gen-elf-golden.sh)
crates/grail            the emulator, RV32 or RV64 per machine (src/cpu: an RV32 hart keeps its registers sign-extended in u64, see src/cpu/mod.rs; rom/diskboot.S: the boot ROM's disk loader, one source preprocessed for each width, which boots a machine started with no program from disk 0)
crates/avalon-proto     Avalon protocol (framing, messages, Connection, Screen diffing), shared by the Avalon platform's programs; spec in docs/avalon-protocol.md
crates/gateway          user-mode NAT gateway (DHCP, DNS, TCP/UDP NAT, hostfwd) with its own frame send/recv API; grail wraps it as a NetBackend for `--net user` (spec 9.8). Must not depend on grail
crates/avalon           the Avalon hypervisor server: VM table, one thread per running VM (run_for slices), consoles, screen viewers and input, RAM budget, virtual Ethernet switches (src/switch.rs)
crates/avalon-client    the client layer: VM control, virtual network and disk management operations, parsers/formatters for addresses, sizes, clocks, disk sources, network cards (shared by Round Table and Pendragon; reuses grail::parse_ram_size/parse_clock)
crates/round-table      the Round Table control CLI: argument parsing and text output over avalon-client (src/lib.rs `run`, main.rs is a thin wrapper)
crates/herald           Herald, the client that attaches to one VM: Session (the console streaming layer, terminal-free), screen::ScreenSession (the screen and input, window-free, drawing through a View) and the CLI, which puts the terminal in raw mode with grail::console::RawMode or shows the screen in grail::window (--screen); tcp::TcpSession and tcp::LineEditor are --tcp, a raw TCP connection with the line edited locally (a shell from kernel/user/shd.c)
crates/lake             the Lake storage server: a directory of disk images served over the protocol (one writer or many readers per image); Grail's client side is grail::lake::LakeDisk
crates/pendragon        the Pendragon web console: std-only HTTP/1.1 server, JSON API and an embedded page over avalon-client; API and security model in docs/pendragon.md
crates/camelot-fs       the Camelot filesystem on the host (docs/camelot-fs.md): format structs, ext4-style extent trees (src/extent.rs: reading, checking and growing them, as kernel/fs.c does), mkfs, fsck and log replay, a reader, the `camelot-fs` command; the kernel's side is kernel/log.c and kernel/fs.c
crates/merlin           the C-subset compiler, C to .s, for RV32 (ILP32, the default until #159) or RV64 (LP64): `-march`, `Options::xlen`; every test program runs on both, `long long` an RV32 register pair with libgcc's division routines in kernel/user/lib/libgcc.c (src/codegen.rs explains the stack frames and code generation, src/abi.rs the calling convention, src/debug.rs what -g writes: .file/.loc and a DWARF compile unit with the functions, their parameters, locals and blocks, the globals and the types; src/preprocess.rs also preprocesses .S assembly as `clang -E -x assembler-with-cpp` does, `merlin -E file.S`, checked against clang by the ignored tests/asm_cpp.rs)
crates/merlin-as        the assembler, RV32 or RV64 per object (`-march=rv32ima_zicsr_zifencei`, the default until #159, or `rv64ima_zicsr_zifencei`; `Options` in the library), writing ELF32 or ELF64 (src/elf.rs); `li` is LLVM's RISCVMatInt (src/encode.rs, ENCODER.md); RV64 references in tests/golden/rv64 and tests/debug_line/rv64, kept out of the RV32 /bin/as's selfhost corpus (scripts/gen-encode-golden.sh, gen-li-golden.sh, gen-hello-ref.sh); src/dwarf.rs turns .file/.loc into .debug_line, byte for byte as LLVM does: tests/debug_line.rs, scripts/gen-debug-line-golden.sh; the $x<isa>/$d mapping symbols are clang's: tests/mapping.rs against clang's objects of tests/mapping (scripts/gen-mapping-golden.sh)
crates/merlin-ld        the linker, ELF32 (RV32) or ELF64 (RV64) executables in the class of its objects, which it reads through the elf crate (src/object.rs checks what it accepts); src/reloc.rs explains every relocation it applies, both widths' rules included; src/layout.rs `AT(lma)` load addresses and `ADDR(section)`; src/write.rs where the segments and headers go, as ld.lld places them; .debug_* sections are kept after everything loaded, and strip_debug/-S takes them out; tests against ld.lld's links in tests/fixtures (the RV32 set, tests/link.rs) and tests/fixtures/rv64 (the RV64 set, tests/rv64.rs; helpers in tests/common), and riscv-tests relinked for both (tests/riscv_tests.rs)
crates/merlin-objdump   the disassembler, RV32 (ELF32) and RV64 (ELF64); output matches llvm-objdump 23 (tests/golden, tests/golden/rv64: scripts/gen-objdump-golden.sh)
crates/merlin-dbg       the debugger: a GDB remote protocol client (src/remote.rs: the machine's width, RV32 or RV64, from the stub's target description) with a command line (src/session.rs), backtraces by frame pointer (src/frames.rs explains the frame layout, RV32's and RV64's), source lines from line tables (src/source.rs: break FILE:LINE, step/next by line, list), variables and types from the debugging information entries (src/vars.rs: print, info locals/args, ptype, whatis, a backtrace's arguments, up/down; tests/vars/vars.c); `-- grail-args` runs a machine in process. Grail's side is grail::debug (the debug interface on Machine) and grail::gdb (the stub, `grail --gdb ADDR`); docs/merlin-dbg.md
crates/xtask            build tasks (`cargo xtask up` builds the platform and runs Lake, Avalon and Pendragon as child processes until Ctrl-C, after seeding Lake's images directory with the bootable root image as `os-base` (`--demo` adds the VM `vm001` on its copy `vm001-disk0`), see src/up.rs; `cargo xtask examples` builds every example with merlin -E + merlin-as + merlin-ld, no LLVM, for RV32 (`<name>.elf`) and RV64 (`<name>-rv64.elf`) from the same .S sources (include/asm.h: REG_L/REG_S/SZREG/RISCV_PTR, the names Linux uses); `cargo xtask kernel` builds kernel/kernel.elf with merlin -g + merlin-as + merlin-ld, no LLVM (line tables in the committed kernels; the embedded and installed user programs stripped, and written with theirs to target/kernel/obj/user/<name>.elf; `-g` changes no loaded byte, tests/debug_info.rs), with the user programs of kernel/user built the same way and embedded through a userprogs.s generated at build time (in memory; a copy goes to target/kernel/obj, never committed), and kernel/kernel-disk.elf, the same kernel without the built-in programs, and `--cc clang` makes the clang -O2 + ld.lld reference build in target/kernel/clang; `cargo xtask fs` builds the root filesystem image target/camelot-fs.img from kernel/fs and the user programs, bootable (bootloader and kernel-disk.elf installed), its size `xtask::fs::IMAGE_SIZE` (the one place to change it; the spec's "Root image" gives it in prose, and the boot test checks the two agree), no LLVM; `cargo xtask boot` rebuilds the committed crates/grail/rom/diskboot.elf, diskboot-rv64.elf and kernel/boot/boot.elf with merlin -E + merlin-as + merlin-ld; `cargo xtask hello` rebuilds merlin-as's ld.lld-linked hello references, RV32 and RV64 (tests/golden/rv64/hello.elf); `cargo xtask ld-fixtures` regenerates merlin-ld's test fixtures with clang and ld.lld, the RV32 set and the RV64 set (src/ld_fixtures.rs: each set's flags, the sources copied into the RV64 set), and `--out DIR` regenerates them into a scratch copy to diff with the committed ones)
kernel/user/as          the assembler that runs on Camelot (/bin/as), merlin-as rewritten in C (line tables included: dwarf.c), a program of several files; tables.h and tables.c are generated from merlin-as's and excalibur's tables by `cargo xtask kernel` (crates/xtask/src/c_tables.rs); crates/xtask/tests/selfhost.rs checks its objects equal merlin-as's
kernel/user/ld          the linker that runs on Camelot (/bin/ld), merlin-ld rewritten in C (no --Map); tables.h and tables.c (relocation names) are generated from the elf crate's by `cargo xtask kernel` (crates/xtask/src/c_tables.rs); crates/xtask/tests/selfhost.rs checks it links every user program as merlin-ld does, and hello assembled and linked on Camelot; both tools' 64-bit arithmetic is kernel/user/lib/i64.c
kernel/                 the Camelot kernel (C + assembly); kernel.elf and kernel-disk.elf (without built-in programs, for bootable images) are committed, rebuild them with `cargo xtask kernel` after changing the kernel, its user programs or merlin, merlin-as or merlin-ld (`cargo test` checks) (kernel/user: the user programs it embeds, C and assembly, and kernel/user/lib their C library, linked like an archive; system calls in docs/camelot-syscalls.md; kernel/net: the network stack, a file per layer, specified in docs/camelot-net.md; kernel/fs: the root image's files; kernel/boot: the bootloader of a bootable disk, which camelot-fs mkfs --boot installs)
include/                asm.h, what assembly writes differently on RV32 and RV64 under one name (REG_L, REG_S, SZREG, RISCV_PTR...: the names Linux's arch/riscv/include/asm/asm.h uses, the definitions this project's; and LWU, ADDW, ADDIW for 32-bit values, its own), for every .S source: the examples, the boot ROM, merlin-ld's fixtures (`-I include`)
docs/                   ISA spec, Avalon protocol, Pendragon API, Camelot system calls, Camelot filesystem format (camelot-fs.md), Camelot network stack (camelot-net.md), merlin-dbg and Grail's GDB stub (merlin-dbg.md)
examples/               bare-metal programs, each built for RV32 and RV64 (`<name>-rv64.elf`, until #159) from one .S source, preprocessed per width (`#if __riscv_xlen == 64`, include/asm.h); their .elf files are committed, rebuild them with `cargo xtask examples` after changes (`cargo test` checks)
tests/riscv-tests       prebuilt riscv-tests ELFs, and obj/ with their objects (merlin-ld relinks them); rv64/ the same for the RV64 suites
```

Reuse `excalibur` (register names, CSR names, decoder, `Inst::format`) and `elf` (reading ELF files, relocation names) instead of duplicating tables.

## Before pushing

CI runs on Linux only (Windows runners are expensive), so Windows is covered by running these checks locally on Windows before every push. Code behind `cfg(windows)`, such as the Win32 window, is only checked here:

```
cargo fmt --check
cargo clippy --all-targets -- -D warnings
cargo test --release
```

`cargo test --release` is the whole suite: run it here before opening a pull request. GitHub's CI runs fmt, clippy and `cargo xtask ci` instead (`crates/xtask/src/ci.rs`): the important tests that take minutes, not the whole suite. Those are the unit tests, the toolchain against its references, the committed binaries current, the kernel booting and the documents. The kernel's filesystem integration tests and their crash tests, and the multi-hart, threads, self-hosting, networking and platform tests, run only here. A new test belongs in `ci.rs`'s list when it is important and quick. The ignored tests need what a plain run may not have, and have their own commands (README.md): a desktop (Grail's and Herald's windows), LLDB, clang and ld.lld (merlin's harness and ABI tests, the coreutils and kernel reference builds), or a quiet machine (Grail's throughput).

A **docs-only** change touches only Markdown (`docs/`, READMEs, this file), and no code, build files, committed binaries or files that go into an image (such as `kernel/fs/`). For one, run only the tests that read documents, not the three checks above:

```
cargo test --release -p xtask --test boot --test fs --test kernel --test up -- the_rom_the_bootloader_mkfs_and_the_documents_agree the_spec_gives_the_root_images_size the_format_document_matches the_system_call_document_matches the_readme_quick_start
cargo test --release -p avalon --test server -- the_readme_client_example
cargo test --release -p lake --test avalon -- the_readme_lake_example
```

A new test that reads a document joins this list, and `ci.rs`'s (`grep -rln '\.md' crates/*/tests` finds them).

Formatting uses `rustfmt.toml` (max width 110). Branch per issue, PR description says `Closes #N`.
