# Pendragon: the web console

Pendragon (`crates/pendragon`) serves a browser page for the Avalon platform: the VMs and virtual switches of an Avalon server and the disk images of a Lake server, with each VM's console and its screen, keyboard and mouse. It is a separate program and a client of both servers over the Avalon protocol ([`avalon-protocol.md`](avalon-protocol.md)), like Round Table, and every operation goes through the same client layer (`crates/avalon-client`): the two front ends accept the same syntax (`--ram`, `--clock`, disk sources and sizes) and cannot drift apart. Avalon and Lake stay headless, and Lake may run on another machine.

Everything is std only and written in the crate: a small HTTP/1.1 server on `std::net` (`http.rs`), JSON (`json.rs`) and base64 (`base64.rs`) for the API, WebSockets (`websocket.rs`, RFC 6455, with SHA-1 in `sha1.rs` for the handshake) for the screens, and the page itself, plain HTML, JavaScript and CSS (`src/ui/`) built into the binary with `include_str!`. There is no frontend build step.

```
pendragon [--listen ADDR] [--avalon ADDR] [--lake ADDR] [--avalon-max-ram SIZE] [--allow-host NAME]...
```

| Option | Default | Meaning |
|---|---|---|
| `--listen` | `127.0.0.1:7402` | where to serve the page (a host alone means port 7402) |
| `--avalon` | `127.0.0.1:7400` | Avalon's address (a host alone means port 7400) |
| `--lake` | `127.0.0.1:7401` | Lake's address (a host alone means port 7401) |
| `--avalon-max-ram` | 4096 | Avalon's RAM budget (its `--max-ram`), in MiB or with `M`/`MiB`, `G`/`GiB` or `T`/`TiB`, for the overview: the protocol does not report it |
| `--allow-host` | | another `Host` the page may be reached by (repeatable; see below) |

Pendragon prints the URL to open on stdout, alone on its line: `http://127.0.0.1:7402/?token=<64 hex digits>`. `cargo xtask up` starts it with Avalon and Lake, and prints the URL again once all three are up (README, *Quick start*).

## 1. Security

Pendragon has no user accounts in v0. It listens on loopback by default, but a browser on the same machine opens other web pages too, and any of them can send requests to loopback. So:

1. **`Host` is checked on every request** (403 otherwise). A page on `evil.example` can make that name resolve to 127.0.0.1 (DNS rebinding) and then read the responses as its own origin; its requests still carry `Host: evil.example`. Accepted are the listening address with its port and, for a loopback or unspecified address, `localhost`, `127.0.0.1` and `[::1]` with the port, plus each `--allow-host` name (with the listening port unless it gives one). Port 80 may also be left out, as browsers do.
2. **Every API request carries the launch's token** in the `X-Pendragon-Token` header (403 `no token` or `wrong token` otherwise). The token is 32 bytes from the operating system's random source, through hand-written FFI to `BCryptGenRandom` on Windows and from `/dev/urandom` elsewhere, made at each launch and compared in constant time. Only someone who saw the printed URL knows it, and a page on another origin cannot send a custom header without a CORS preflight, which Pendragon never grants. The page takes the token from its URL, keeps it in the tab's `sessionStorage` and removes it from the address bar.
3. **Requests that change something** (anything but `GET` and `HEAD`) must not come from another origin: an `Origin` header, when the browser sends one, must be `http://` and an accepted host. Their bodies must be `application/json`, which a plain HTML form cannot send.

   **A screen's WebSocket** (section 3, **Screens**) is opened with a `GET`, but takes the same `Origin` check: there is no CORS for WebSockets, so a browser lets any page open one to any server (cross-site WebSocket hijacking), and the browser always says which page it is. A page cannot set headers of its own on a WebSocket's handshake, only the subprotocols it offers (`Sec-WebSocket-Protocol`), so the page offers two, `pendragon.screen` and `pendragon.token.<token>`, as Kubernetes passes its bearer tokens; Pendragon answers `pendragon.screen` and never repeats the token, and takes the token from a subprotocol on this route only (anywhere else it must be in the header). A client that can set headers may send `X-Pendragon-Token` instead and offer no subprotocol. Once open, the WebSocket is the page's for as long as it stays: the checks are made once, on its handshake.

These checks are made on the request line and headers alone, before Pendragon reads the body or makes room for it: a refused request costs its head, whatever `Content-Length` it announces. A body that passes is read into a buffer that grows as the bytes arrive, not one made full size up front.
4. **Output is inert.** The page's script builds every element with the DOM and sets data only as text (`textContent`), never as markup; the JSON encoder also escapes `<`, `>`, `&`, U+2028 and U+2029. Every response has `Content-Security-Policy: default-src 'none'; script-src 'self'; style-src 'self'; connect-src 'self'; img-src 'self'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'` (no inline script or style at all; `connect-src 'self'` covers the page's own `ws://` URLs too: in CSP Level 3, `'self'` matches `ws:` on the page's host and port when the page is `http:`), `X-Content-Type-Options: nosniff`, `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer` and `Cache-Control: no-store`.

The static page (`/`, `/app.js`, `/style.css`) needs no token: it is the same for everyone and holds no data.

Listening on another interface (`--listen 0.0.0.0`) takes `--allow-host` for the names the page is reached by, and Pendragon warns at startup: the token is then all that stands between the network and the VMs, over plain HTTP.

## 2. HTTP

One request per connection; every response says `Connection: close`, but for the `101 Switching Protocols` that makes a screen's connection a WebSocket (section 3, **Screens**), which stays open for it. The parser is strict, so that it never guesses differently from another program:

| Request | Answer |
|---|---|
| request line and headers over 16 KiB (every CRLF counted, the blank line that ends them too), or more than 64 header lines | 431 |
| a bare LF, a folded header, whitespace before a header's colon, control or non-ASCII bytes in the head, a target that is not a path or has a fragment, a bad `%` escape | 400 |
| HTTP/1.1 without exactly one `Host` | 400 |
| `Transfer-Encoding` (chunked bodies) | 501 |
| two `Content-Length` headers, or one that is not a number | 400 |
| a body longer than its route allows (64 KiB; 24 MiB for creating a VM, whose program travels in base64) | 413, before any of the body is read |
| `Expect` other than `100-continue` | 417 |
| an HTTP version other than 1.0 and 1.1 | 505 |
| a screen's route (`/api/vms/{vm}/screen`) asked for without `Upgrade: websocket`, or for a WebSocket version other than 13 | 426, with `Upgrade: websocket` or `Sec-WebSocket-Version: 13` (RFC 6455 section 4.4) |
| a WebSocket handshake that is not HTTP/1.1, lacks `Connection: Upgrade` or a `Sec-WebSocket-Key` that is the base64 of 16 bytes (once), has a body, or offers subprotocols without `pendragon.screen` | 400 |
| the whole request not in within 30 seconds, however slowly it trickles in | 408 |
| more than 64 connections at once | 503 (answered off the accepting thread, at most 16 at a time; past that the connection is closed) |

One empty line (CRLF) before the request line is ignored, as RFC 9112 section 2.2 asks. After its response, a connection reads and drops what the client still sends for at most a second (and 4 MiB) before it closes, so that closing does not reset the connection before the client has read the response; a client that keeps sending cannot keep the connection longer.

## 3. API

Every route is under `/api/`, takes and returns JSON (`Content-Type: application/json`), and needs the token. Errors are `{"error": "<message for a person>", "code": "<protocol error name, or null>"}`; the status follows the protocol's error code:

| Status | When |
|---|---|
| 400 | the request itself is wrong: bad JSON, a missing or unknown field, a value Round Table would refuse too (`ram: 0 is out of range (1 MiB to 1 TiB)`) |
| 403 | the checks of section 1 |
| 404 | `NoSuchVm`, `NoSuchDisk`, `NoSuchSwitch`, `NoSuchCard`, an unknown route |
| 405 | a route that does not take that method |
| 409 | `AlreadyExists`, `Busy`, `InvalidState`, `OverBudget`, a detach with nothing to detach, an unplug from a switch the card is not on |
| 422 | `InvalidName`, `InvalidProfile`, `InvalidProgram` |
| 502 | a server that cannot be reached, or another protocol error (`Io`: a gateway's host port that cannot be bound, say) |

A VM in a path (`{vm}`) is its id (all digits) or its name, as on Round Table's command line.

| Route | What |
|---|---|
| `GET /api/overview` | both servers' health (`ok`, `server` name or `error`), VM counts by state (`created`, `running`, `paused`, `debug`, `ended`), RAM in use (the sum of every VM's RAM, which Avalon holds from create to destroy) against the budget, disk count, attached count and total size, `consoles`: how many consoles Pendragon has open, and `screens`: how many screens |
| `GET /api/vms` | every VM: `id`, `name`, `state` (`created`, `running`, `paused`, `debug`: stopped by a breakpoint, a watchpoint or a debugger's step (protocol doc, section 6.8), `stopped`, `exited`), `state_text`, `exit_code`, `paging` (`sv48` or `sv39`) and `arch_text` (`RV64 (Sv48 and Sv39 paging)`), `bios` (the firmware: `none`, `default` or a file's path), `ram`, `clock_hz` (null: full speed), `nominal_hz`, their `*_text` forms, `harts`, `disks` (`source`, `read_only`, `lake`: `{addr, name}` or null, `held`: whether the VM still holds it), `nets` (`card` number, `mac`, `switch` it is plugged into or null, as they are now) and the `actions` its state allows |
| `POST /api/vms` | create: `{"name", "paging", "bios", "ram", "clock", "harts", "disks": [{"source", "read_only"}], "nets": [{"switch", "mac"}], "profile", "camelot", "program", "start"}`. `paging`, `bios`, `ram`, `clock` and `harts` are text as Round Table's `--paging`, `--bios`, `--ram`, `--clock` and `--harts` take them (`sv48` or `sv39`; `none`, `default` or a firmware file on Avalon's host; MiB, or with `M`/`MiB`, `G`/`GiB` or `T`/`TiB`, 1 MiB to 1 TiB; `10MHz`, `500kHz`, `5Hz`; 1 to 8; empty for the defaults: Sv48, no firmware, 4 MiB, full speed, one hart; a Camelot VM has its profile's firmware and RAM, Camelot's firmware and 6 MiB (its 2 MiB on top) for a server, 64 MiB for a desktop, unless they say otherwise). Every VM is RV64: there is no width to choose (an `xlen` is an unknown field, 400), each disk source a path on Avalon's host or `lake://ADDR/NAME`, each network card's switch a name (empty or null: unplugged) and its `mac` `xx:xx:xx:xx:xx:xx` (empty or null: Avalon makes one up), as `--net SWITCH,mac=...` takes them; the cards come after the disks in the profile. `program` is the ELF file in base64; it may be left out when there is a disk, and the VM boots from the first. `profile` (`server` or `desktop`; empty or null: none) makes a Camelot VM of that hardware profile instead, as `round-table create --profile` does: Lake copies the profile's image, `os-base` or `os-desktop`, to `<name>-disk0` (see below), which goes before the other disks, and the VM boots from it; it takes no `program` (400). `camelot: true` is `profile` `server`; both together, or a profile with no such name (`profile: no profile 'NAME' (server or desktop)`), are 400. 201 `{"id", "name", "started", "disk"}`, `disk` the Camelot VM's copy or null |
| `GET /api/vms/{vm}` | one VM, as in the list, plus `steps` and `devices` (the guest's sysinfo table) |
| `POST /api/vms/{vm}/{action}` | `start`, `pause`, `resume`, `stop` or `destroy` |
| `GET /api/vms/{vm}/console?from=N&tap=T&wait=MS` | console output from byte offset `N` (below) |
| `POST /api/vms/{vm}/console` | `{"data": "text"}`: bytes for the VM's UART |
| `GET /api/vms/{vm}/screen` | a WebSocket: the VM's screen, keyboard and mouse (below) |
| `GET /api/disks` | `lake` (Pendragon's Lake), `profiles`, the hardware profiles of Camelot VMs (`avalon_client::PRESETS`), each `{"name", "about", "image", "ram", "bios"}`: its name (`server`, `desktop`), a line on what it is for, the image its VM's disk is a copy of (`os-base`, `os-desktop`), its RAM in MiB unless told otherwise (6, 64: the new-VM form's until it is typed in) and its firmware unless told otherwise, as `bios` takes it (`default`: the form's *Firmware* for a Camelot VM until it is typed in), and every Lake image: `name`, `sectors`, `bytes`, `size_text`, `readers`, `writer`, `attached`, and `attached_to`: the VMs on Pendragon's Avalon that hold it (`id`, `name`, `read_only`; each VM once, read-only only if every disk of it that names the image is), or null when Avalon cannot be asked (`vms_error` says why) |
| `POST /api/disks` | create: `{"name", "size"}`, the size as `disk create --size` takes it (`64MiB`, `512K`, `1G`, `2048s`). 201 |
| `DELETE /api/disks/{name}` | delete an image nobody has attached (409 `busy` otherwise) |
| `POST /api/disks/{name}/detach` | stop the VMs on Pendragon's Avalon that hold the image (see below); `{"stopped": [{"id", "name"}], "released": bool}` |
| `GET /api/switches` | every switch of Avalon, in name order: `name`, `capture` (the pcap file or null), `nat` (null, or the gateway: `network`, `gateway`, `dns`, `hostfwd`: its rules as bound, `tcp:127.0.0.1:8080-10.0.2.15:80`, and `leases`: `addr`, `mac` and the `vm` (`{id, name}` or null) whose card has that address), and `ports`: `kind` (`card` or `gateway`), `vm` (`{id, name}`, the name null if the VM is not in the list), `card`, `mac`, `in_frames`, `in_bytes`, `out_frames`, `out_bytes`, `dropped`. `vms_error` says why the VMs are unknown, when they are |
| `POST /api/switches` | create: `{"name", "nat": bool, "hostfwd": ["RULE", ...]}`, each rule as `switch create --hostfwd` takes it (`[tcp\|udp]:[HOSTADDR]:HOSTPORT-[GUESTADDR]:GUESTPORT`; the host address defaults to 127.0.0.1, the guest to 10.0.2.15; host port 0 lets the system pick). Forwarding ports needs `nat` (400 otherwise). 201 `{"name", "nat"}`, `nat` as in the list with the ports as bound |
| `DELETE /api/switches/{name}` | delete a switch: its cards are unplugged, its gateway ends and its host ports are closed before the reply |
| `POST /api/switches/{name}/nat` | give the switch a NAT gateway: `{"hostfwd": [...]}`; 409 `already exists` if it has one. `{"name", "nat"}` |
| `DELETE /api/switches/{name}/nat` | take its gateway away (409 `invalid state` if it has none), closing its connections and host ports |
| `POST /api/switches/{name}/attach` | plug a VM's card in: `{"vm": id or name, "card": N}` (card 0 if left out); a card on another switch moves |
| `POST /api/switches/{name}/detach` | unplug it: the same body; 404 for a switch or a card that does not exist, 409 for a card on another switch or none |

**Attaching and detaching disks.** A VM's disks are part of its hardware profile, fixed when it is created; the protocol has no hot-plug (protocol doc, section 6.6). So attaching a disk is creating a VM with it (the disk page's *attach* opens the new-VM form with the image filled in), and a VM lets go of its disks when its machine ends: detaching stops the VMs that hold the image, then waits up to 5 seconds for Lake to show it released (`released`). A stopped VM cannot be started again, which the page says before it detaches. A VM holds a Lake image when it is created, running, paused or in state debug and its profile names the image on a server that is Pendragon's Lake: the same address, or one that resolves to the same socket address (`localhost:7401` and `127.0.0.1:7401`). An image attached by a client Pendragon does not manage (another Avalon) shows as attached with no VM, and cannot be detached here.

**Camelot VMs.** The new-VM form chooses the VM's paging (Sv48 and Sv39, or Sv39 alone) and firmware (*Firmware*, sent as `bios`: `none`, `default` or a firmware file on Avalon's host; it follows the choice until it is typed in, the profile's `bios` for a Camelot VM and `none` for a program, so an uploaded `kernel.elf` needs `default` typed or picked), and what the VM boots: *Camelot (boot from disk)*, as a server or a desktop (the profiles from `GET /api/disks`, sent as `profile`; the RAM follows the profile too until it is typed in), or *Program (ELF)*. Camelot is chosen when Lake has a profile's image (`os-base`, `os-desktop`, which `cargo xtask up` puts there), as the first profile whose image it has, and the form was not opened to attach a disk; its hint names the profile's image, and without it says to run `cargo xtask up`. A Camelot VM's image boots on Camelot's firmware (`bios` `default`, which a Camelot VM has unless told otherwise), in S-mode. A Camelot VM's create is two steps on two servers, through `avalon_client::create_camelot_vm`, the function Round Table's `create --profile` uses: Lake copies the profile's image to `<name>-disk0` (a `DiskCreate` with a source, protocol section 6.6), then Avalon creates the VM with `lake://<Pendragon's Lake>/<name>-disk0` as disk 0 and no program, so it boots from the disk. Lake allows one writer per image, so every Camelot VM needs a copy of its own, and two of them run side by side. A missing image is 404 (`no such disk`, with the hint), a copy whose name is taken 409 (`already exists`), an image another VM writes 409 (`busy`); when Avalon refuses the VM (its name is taken, the RAM budget), the copy is deleted again and the status is Avalon's. A name too long to leave room for `-disk0` in a disk name is 400. The request is a change like any other: same token, `Origin`, `Host` and JSON-body checks (section 1).

**Switches.** The switches page lists Avalon's switches with each port's counters, creates one (with a NAT gateway and its forwarded ports, one rule per line), gives a switch a gateway or takes it away, deletes one, and plugs a VM's card in or unplugs it. Every one of these is a change, under the same token, `Origin` and JSON-body checks as the rest (section 1): forwarding a host port opens a socket on Avalon's host, so another site must not be able to ask for one. A forwarded port is bound on 127.0.0.1 unless its rule names another address. The new-VM form adds network cards (a switch and an optional address each).

**Consoles.** A browser cannot speak the Avalon protocol, so Pendragon attaches to a VM's console for it: a *tap* is one protocol session attached to one VM (`ConsoleAttach`), with a thread reading its output into a buffer of the last 64 KiB. Every page showing the VM shares the VM's tap; a tap nobody has read or written for a minute is closed (a thread looks every few seconds, whether or not anyone opens another console), and at most 32 are open (409 `over budget` past that). A read returns `{"vm", "tap", "from", "next", "data", "reset", "ended"}`: the output from offset `from` (counted from the start of the tap, the scrollback Avalon sent on attaching at 0) to `next`, in base64 (`data`), so console bytes that are not UTF-8 arrive as they are. The page asks again from `next`. A read with nothing new waits up to `wait` milliseconds (at most 20 seconds) for output, so text shows up as soon as the guest writes it (long polling). A read with another tap's number (Pendragon restarted, or the tap was closed) starts again from the oldest byte with `reset` set; a `from` that is older than the buffer gets what is left. `ended` says why the session ended (the VM was destroyed, Avalon went away). Input goes to the VM as `ConsoleInput`, in pieces of at most 4 KiB.

**Screens.** The VM's page shows its screen in a `<canvas>` and sends it the page's keyboard and mouse, as Herald's `--screen` window does. A browser cannot speak the Avalon protocol, so Pendragon is the VM's viewer for the page (protocol doc, section 6.4): `GET /api/vms/{vm}/screen` is a WebSocket (RFC 6455, subprotocol `pendragon.screen`), and each one is a protocol session of its own, attached to the VM's screen (`ScreenAttach`). So Avalon keeps every page's keys and buttons apart from the others' and from Herald's, and lets go of them when the page goes, as it does for any viewer. Pendragon attaches before it answers the handshake: a VM that does not exist (404), an Avalon that is away (502) or a screen it cannot relay (502) is an HTTP error, and so is a 17th screen open at once (409 `over budget`; `ScreenLimits::max_screens`, 16, each a connection of the 64, a session with Avalon and two threads). The checks of section 1 come first.

What Pendragon sends:

| Message | When | What |
|---|---|---|
| `{"type": "screen", "vm", "width", "height"}` (text) | first, and on every `ScreenResized` | the screen's size: the canvas starts again, black, at it (the guest changed modes); a full frame follows |
| `{"type": "state", "state", "state_text", "exit_code"}` (text) | after the first `screen`, and on every `VmStateChanged` | the VM's state, in the words of `GET /api/vms` |
| binary | one per `ScreenFrame` | a rectangle of the screen: `x`, `y`, `width`, `height` (`u32`, little-endian), then its pixels as a canvas's `ImageData` takes them, R, G, B and A bytes (A 255), rows top to bottom. The page draws it with `putImageData` |
| `{"type": "cursor_shape", "width", "height", "hot_x", "hot_y", "pixels"}` (text) | one per `CursorShape`: after the full frame when the cursor has an image, and whenever the guest gives it a new one | the cursor's image from now on (below), kept while the cursor is hidden and across a `screen`: `width` × `height` pixels (1 to 256 each way), in base64 as `ImageData` takes them, straight R, G, B and A bytes, rows top to bottom; its hotspot at (`hot_x`, `hot_y`), which the page does not use (the image is placed by its top left pixel) |
| `{"type": "cursor_position", "visible", "x", "y"}` (text) | one per `CursorPosition`: after the image when the cursor shows, and whenever it moves, shows or hides | whether the cursor shows, and where: its image's top left pixel at (`x`, `y`) of the screen, negative or past its size for an image that hangs off an edge (`x` and `y` mean nothing while it is hidden) |
| `{"type": "end", "reason"}` (text) | the VM stopped, exited or was destroyed, Avalon went away or sent something broken, Pendragon is shutting down | then a close frame with the same reason: 1000 for the VM's end, 1011 for Avalon's, 1001 for Pendragon's |

**The cursor.** The guest's cursor (the display's cursor plane, Excalibur spec section 9.3) is not in the frames: Avalon sends it to its viewers apart from them (protocol doc, section 6.4, **Cursor**), and Pendragon relays each message as it comes, so a cursor that moves costs a message of a few dozen bytes and redraws no frame. A page that opens gets the cursor as it is after the full frame, as any viewer does. The page draws it on a second canvas of the screen's size, transparent, laid over the screen's at the same scale (`pointer-events: none`, so the pointer's events go through to the screen's): a move clears the rectangle the cursor was drawn in and puts its image at the new place, and the browser blends the two canvases. The guest's image is ARGB8888 with premultiplied alpha, but `ImageData` is straight RGBA, so Pendragon divides each colour by its alpha, `c × 255 / A` rounded to the nearest (`screen::straight_rgba`). A canvas keeps its pixels premultiplied, so `putImageData` multiplies back, `c × A / 255`, and rounded to the nearest that is the guest's colour exactly (the division is off by less than half, times `A / 255`); the browser's source-over is then the spec's OVER, `cursor + screen × (255 − A) / 255`. Two kinds of pixel straight alpha cannot hold: one whose colour is above its alpha (the spec's sum saturates) is drawn at full colour, and one with colour and A = 0 (which the spec adds to the screen) is transparent. The guest's ordinary cursors (premultiplied, as KMS's and Wayland's are) have neither.

A screen whose VM has stopped or exited sends its last frame, and the cursor, and ends at once, as Herald's does. What the page sends, text messages in JSON (each field required, no other allowed; anything else closes the WebSocket with 1008, a binary message with 1003, one over 4 KiB with 1009):

| Message | What |
|---|---|
| `{"type": "key", "down", "code", "key", "shift", "ctrl", "alt"}` | a `keydown` or `keyup` on the canvas: `KeyboardEvent.code`, `.key`, `.shiftKey`, `.ctrlKey`, `.altKey` |
| `{"type": "pointer", "x", "y", "buttons"}` | a `pointerdown`, `pointermove` or `pointerup`: the position in the screen's pixels (the canvas may be drawn smaller), `PointerEvent.buttons`; `x` and `y` may be left out together, for a change of buttons alone |
| `{"type": "wheel", "dy", "mode"}` | a `wheel` event: `deltaY` and `deltaMode` |
| `{"type": "release"}` | the canvas lost the focus, or the tab was hidden |

Pendragon turns them into `KeyInput` and `PointerInput` with the rules of Grail's window, so the page has no key table of its own:

- A key carries both of the keyboard's forms (protocol doc, `KeyEvent`): the physical key, the HID usage that `grail::keyboard::usage::from_dom_code` gives its `code` (the guest's raw mode), and the character typed, from `key` (ASCII mode): a printable ASCII character is itself, `Enter`, `Tab`, `Backspace`, `Escape`, the arrows and `F1` to `F12` the spec's codes (Excalibur spec section 9.4), anything else 0. Browsers report the character without Ctrl's effect (Ctrl+C is `c`). Shift and Ctrl go with it; Ctrl with Alt is AltGr on Windows, a character and not a Ctrl chord. A key with neither form sends nothing; one with no `code` is told apart by its `key`.
- A key's release carries what its press had (the `q` of a `q` released after Shift went down); a key down again before it was up is the browser's auto-repeat, sent with the repeat flag (another press in ASCII mode, nothing in raw mode); a key-up of a key never seen down (held when the page got the focus) sends nothing. Print Screen, whose key-down Windows keeps for itself, comes as its key-up alone and is sent as a press and a release; so are Lang1 and Lang2, the make-only Korean keys.
- On `release` every key the page holds is released, with the code of its press, and the buttons are released if any were held: the key-ups now go elsewhere, and a guest must not be left with Alt down. The page sends it when the canvas loses the focus (to another element, another window) and when the tab is hidden. A page that closes, or whose connection ends, needs no `release`: Avalon lets go of what that viewer held.
- A pointer position past the screen's edges (a drag that left the canvas, which pointer capture keeps reporting) is clamped to them. Of `buttons`, bits 0 to 2 (left, right, middle) are the protocol's own; the back and forward buttons are left out.
- The wheel turns as noVNC turns it into VNC's wheel buttons: lines and pages count 19 pixels each, the pixels add up until they make 50, which is one notch, and the rest is dropped; a turn the other way starts afresh, as in Grail's window. `deltaY` is positive towards the person, a notch away from them.

The page stops each key's default action while the canvas has the focus, so Tab, Backspace and F5 are the guest's (the few a browser keeps, such as Ctrl+W, never reach a page). On Windows a browser reports AltGr as a Left Ctrl that is not there and Right Alt, together: the page holds a Left Ctrl press back for up to 100 ms and drops it when a Right Alt press follows within 50 ms, as noVNC does. A press of the pointer focuses the canvas, captures the pointer and stops the default action (no text selection, no middle-button scrolling); the context menu is the guest's right button.

A page that has sent nothing for 20 seconds is pinged (`ScreenLimits::ping`), and one that has not answered 20 seconds later is gone (its machine slept, its network went away): the screen is closed with 1001. Pendragon answers the page's pings and close frames as RFC 6455 says, and checks its frames: masked, no reserved bits (no extension is agreed), control frames whole and at most 125 bytes, text in UTF-8, close codes the RFC allows (1002 and 1007 otherwise). A page that takes nothing of what Pendragon writes for 10 seconds is dropped: frames go out 16 KiB at a time, and each piece must be taken within 10 seconds of the one before, however long a whole frame takes over a slow link (the same on Windows and Linux, whose socket timeouts mean different things). When its WebSocket ends, Pendragon detaches from the screen (`ScreenDetach`) and closes its session with Avalon. The page connects again 3 seconds after a WebSocket that closed without an `end` (Pendragon restarted, Avalon away).

## 4. Tests

`crates/pendragon` has unit tests for the HTTP parser (good requests, every malformed shape above, oversize heads and bodies, `100-continue`, a request split into single bytes, a slow client against the deadline), JSON (the grammar's corners, escapes, surrogates, depth, duplicate keys, exact numbers), base64, the random source, the guard (hosts, tokens, a token in a subprotocol on the screen's route only, origins, `--allow-host`), the request parsing of the API and the command line. `tests/api.rs` runs Avalon and Lake in process and drives every operation over HTTP: disks created, listed and deleted; a VM created on a Lake disk with an uploaded program, Camelot VMs created with no program (`tests/camelot.rs`: two at once on copies of their own, with extra disks, a desktop by its profile, the refusals, and the page's form), listed, inspected by id and by name, taken through its states; the disk shown attached to it, refused for deletion and for a second writer, then detached; read-only images shared by two VMs; the console's output, input, long polling and reset; refusals with their codes; servers that are away; switches created with and without a NAT gateway, a VM with two cards running `examples/net/net-user` whose lease names it, cards unplugged and plugged back, a gateway given and taken away, a taken host port refused, and a deleted switch's forwarded port free again. `tests/screen.rs` speaks WebSocket to Pendragon as the page does: `examples/colorbars` reaches the canvas pixel for pixel as Grail draws it, with the VM's states and the end; `examples/flip`'s mode change resizes it to 800x600; `examples/kbd-echo` in raw mode prints the physical keys a page sends (Shift alone, a release with its press's usage, auto-repeat dropped, every held key released on `release`, and Right Ctrl released by Avalon when the page closes); `examples/pointer`'s cursor follows moves and clicks, and a drag past the screen's edge; `examples/cursor`'s cursor plane comes once as a `cursor_shape`, then as `cursor_position`s at the places Grail's cursor registers held, in their order, to the last, with no frame after it shows, and the canvas with the cursor's canvas blended over it (as a browser blends them) is what Grail's display shows, pixel for pixel, for a page open from the start and one opened after the end. It also checks refused handshakes (`Host`, token, a token's subprotocol on another route, `Origin`, method, version, subprotocol, no such VM, Avalon away), pages that break the rules (an unmasked frame, an unknown message, a binary one, one too large), pings, the screen limit and the close on shutdown; `screen.rs`'s unit tests have the key, pointer and wheel rules, the cursor's messages and its straight image (every premultiplied colour and alpha back as it was once multiplied again, saturated and transparent pixels) and a page that gets nothing after a failed write, and `websocket.rs`'s the handshake and framing (RFC 6455's own examples) and SHA-1 (FIPS 180's vectors). `tests/security.rs` checks the page's headers and script, wrong `Host`s, missing and wrong tokens (on the switch routes too), foreign origins (one asking for a forwarded port among them) and form bodies, escaped output, malformed, oversize and slow requests, and the connection limit. `tests/cli.rs` runs the binary and uses the URL it prints.
